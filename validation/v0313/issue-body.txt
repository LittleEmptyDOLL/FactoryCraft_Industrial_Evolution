# FactoryCraft 0.31.1 — High-speed train crash and Create-parity rail placement fixes

## Source, scope, and ordering
User reports **new in-game failures after issue #13 continuation**: game crashes when accelerating a train to roughly **120 km/h**; bushes/torches and similarly non-solid blocks prevent laying rail; no Create-style allowable-endpoint area is shown; rotating the camera does not rotate a candidate rail's destination tangent, making turns unnecessarily difficult. **Investigate and correct these issues**, using the **current latest main** (at drafting `37cd9988a65e13e18a2d4b8982fdd6d3b79a7ef5`) and the real 1.21.1 Create source as a **technical/interaction reference**, not as a mandatory dependency or mechanics authority.

This is a **focused 0.31.1 hotfix/UX milestone**; do not start 0.32 signals/stops/schedules, introduce new rail types, rework Factorio 2.1+Space Age progression, or discard already-tested 0.30/0.30.1/0.31 resource ownership. Keep issue #13 linked and honest about any remaining broader visual acceptance.

## 2. Rail placement: non-colliding and replaceable blocks
Concrete code finding: `RailPlan.inspect()` currently rejects every `!state.isAir() && !state.is(RailContent.BED.get())` cell across the **entire swept train-clearance volume**. `RailPlacement.place()` likewise does not properly handle legally replaceable bed cells. As a result, a torch, grass/bush/flower, etc. is rejected without regard for physical rail/train collision.
- Separate **railbed voxels**, **vehicle swept clearance**, and **support/permission checks**. A non-solid block with **empty collision shape** outside the physical bed must not block a future carriage even if it is not air. In the bed footprint, use NeoForge/Minecraft valid `canBeReplaced`/tags and **actual occupied voxel shapes**, respecting support and safe replacement rules. Distinguish tall grass, flowers/bushes, torches, snow layers, vines and non-colliding foliage from solid/full-collision glass, walls, machines, chests, claimed/protected or other actual obstacles. Transparent material does NOT automatically mean passable: glass with real collision stays blocking.
- Handle replaceable bed-block replacement through the same **protected atomic server transaction** including drops/removal semantics; preserve any existing block entities/resources, world protection / NeoForge cancel events, rollback, material ledger and ghost preview agreement. Do not silently erase player-owned blocks or produce duplicate drops. If client cannot know a server claim, preview remains advisory and server rejects with localized reason.
- Keep `TrainWorld.contact` and world placement hooks consistent: a torch/plant that placement newly accepts must not immediately stall the train. Do not globally allow liquids, solids or mixed railroad/foreign tracks; clearly document waterlogged/plant special cases.
- Validate all 16 headings, starter, curves, slopes, tunnels, behind/above supports, same-level crossings, editable existing tracks and chunk boundaries with real GameTests for harmless/replaceable vs colliding blocks.

## 3. Destination tangent follows the camera, like Create
Direct comparison: both `RailPlanner.click` (around lines 141–149) and `RailClient.render` (around 168–175) use `goal < 0 ? RailHeading.nearest(delta.x(), delta.z()) : new RailHeading(goal)`. This forces the end tangent toward/from the original anchor rather than following the player's camera. The client preview cache key only includes origin/end, not the **look heading**.
- On supported-ground destinations, derive the **end tangent from camera yaw** projected to the closest of FactoryCraft's **16 Factorio 2.1 heading families** (cardinal/diagonal/half diagonal). On existing rail endpoints, snap to the chosen actual rail tangent; don't incorrectly rotate already laid track. Starting tangent should stay the selected rail endpoint; the destination orientation responds visibly, live, to camera rotation **even when the crosshair remains on the same block**.
- Fix preview invalidation/cache key to include camera heading, manual direction overrides, start/end state, loaded rail changes; client and server must compute exactly the same candidate (authoritative validated action). Retain optional explicit `R` cycle and `X` flip as understandable overrides/reset controls, don't make them the only way to lay a turn. Any override should have predictable reset behavior when a new selection starts.
- Make the single-player gesture intuitive: select existing endpoint → hover ground and turn camera → preview curve adjusts → click confirms; a blocked/too-sharp route shows red ghost and reason rather than disappearing. After success clear selection, `C`/sneak cancels, no stale anchors. No arbitrary radius reduction below 13 blocks or train proportion changes.
- Add tests for rotating view 45°/90°/half diagonals with unchanged destination block; compare full client preview geometry/heading and server committed edge; old tracks/turnouts preserve valid snapping, permissions, cost, rollback and replay protection.

## 5. Accurate rotated train collision / oversized footprint on turns (required)

**Additional user-observed bug:** when the locomotive or wagon rotates on a curved/diagonal rail, its effective collision/interaction region becomes **far too large** compared with the visible 3D vehicle; nearby walls/objects or another train may register false contact. Fix alongside the placement/120-km/h problems, not in a later feature milestone.

### Confirmed current implementation points (inspect latest code, not only line references)
- `TrainWorld.box(BogiePose)` turns an oriented 3×7×4 envelope into a **world-axis AABB** via absolute projected axes; this necessarily expands sideways on corners.
- `StockEntity.authoritative()` sets that expanded box on the vanilla entity, and client `StockEntity.updateBox()` uses yaw-expanded 7×3 AABB as well. Thus vanilla entity picking/collision/interactions may use the enormous box even though the custom server narrowphase is better.
- `StockEnvelope.of()` already implements **oriented SAT**, but the current 3×7×4 is conservative relative to the documented visual stock (~2.16×7×3.42); `TrainWorld.contact()` uses SAT for broadphase candidates, yet `SpatialReservations.canReserve()` treats intersecting swept **axis-aligned** aggregate bounds as definitive train conflicts without an oriented narrowphase.
- `RailFootprint` voxelizes axis-aligned envelopes for construction clearance and `RailPlan.inspect()` rejects every occupied voxel. This reserves a visibly exaggerated empty wedge around turns and produces false builder obstruction, even when a legal vehicle would physically clear a nearby block.
- `TrainWorld.sweep()` unions intermediate AABBs plus a 0.25-block margin, which can exaggerate turns and adjacent-track occupancy; this must remain temporally safe, but not be the sole final collision decision.

### Required design, without breaking train protection
1. **Single shared stock geometry model:** verify actual locomotive/cargo/tanker meshes and collision dimensions in `StockRenderer`, `StockSpec` and `StockEnvelope`; use a consistent oriented body (OBB with a small justified safety margin) centered on the **actual car pose sampled from its two bogies**, including pitch on grades. Where shapes warrant, use a small compound set of oriented hulls; wheel/bogie coupling can use separate smaller shapes. Preserve Factorio original model proportions and full body clearance, not arbitrary undersized hulls.
2. **Broadphase ≠ collision.** Keep cheap AABBs for querying nearby chunks, blocks, entities and candidate train owners; require **narrowphase** intersection (OBB/SAT against block `VoxelShape` sub-AABBs, real neighboring entities, and other stock OBBs) before declaring collision/damage/occupation. Account for rotated and inclined boxes; no fixed axis-aligned rectangle is authoritative on a bend. Use conservative swept time samples / continuous motion checks to prevent high-speed tunneling.
3. **Reservations:** `SpatialReservations` must not reject two trains on properly separated adjacent curved lines purely because their conservative AABBs overlap. Retain exclusive same-edge intervals, switch/fork conflict zones and genuinely overlapping swept bodies; use staged swept-oriented shape checks or equivalent robust conservative route-conflict test for adjacent rails, without O(N²) all-train scans. Do not weaken protected junction/headway rules to eliminate false positives.
4. **Entity handles/interaction:** Vanilla still expects an entity AABB for spatial lookup. If a broad entity box is unavoidable, keep it only for candidate discovery/selection and perform precise oriented narrowphase for actual impacts/attack/hit selection/interaction; if narrowing it, explicitly ensure full-model hit detection remains possible. Audit vanilla collision/pushing/rider dismount/selection behavior, turret and player projectile hits, loaded-chunk membership and spatial claims. A player beside the outer corner of a rotated AABB but **outside** the body must not be struck or blocked; a real hit against the chassis must be detected.
5. **Construction clearance:** align `RailFootprint`/builder preview and world placement validation with the **same tested swept oriented full-sized train geometry** used at runtime. Remove artificial empty triangular AABB regions while still denying actual solid interference, tunnel wall collisions and genuinely insufficient radii. For high-speed turns, include appropriate real motion/coupler clearance, not a square centered on each rail point. Reconcile separately with the replaceable plant/torch fix elsewhere in this issue.
6. **Visualization/debugging:** optional toggleable diagnostic wireframe for **visual mesh**, precise oriented collider, broadphase AABB, and future-path swept clearance in different colors. Debug only, not mandatory visible during normal play or global per-tick debug rendering. Verify with real screenshots in Minecraft that hull matches each wagon when turned 0°, 22.5°, 45°, 67.5° and 90°, on S bends and ascents/descents.
7. **Safety/performance:** save unchanged canonical car/train IDs, inventory/fluid/fuel and movement; do not introduce per-block live collision entities or N×world scanning. Cache immutable hull geometry and use scalar SAT/voxelshape bounds with measured allocation and world-read budgets. Re-run affected native chunk, network, damage/impact, train split, head-on, fork, tunnel and long-consist tests.

### Additional acceptance scenarios
- Tight but physically legal curved railway **next to a solid wall**: a model that clears the wall at 0°/45°/90° continues without invisible collision; move the wall into the actual swept chassis and the train safely stops/impacts.
- Two neighboring curved tracks: no ghost overlap/reservation deadlock when actual rotated hulls are separate; true close conflict must still stop/avoid damage according to existing occupancy policy.

## 6. Train-vs-entity impacts must preserve momentum (new user-reported defect)

**User observation:** at maximum locomotive speed, hitting an ordinary Minecraft mob **instantly sets the train speed to zero**. This must not happen merely because the collision detector found a living entity. Preserve Factorio 2.1 + Space Age train behavior: high-speed trains can run down weak enemies and **continue**, while strong/undefeated obstructions and accumulated collisions can slow or stop a consist. No fantasy no-collision/invulnerable-train option.

**Confirmed direct cause in current code:**
- `TrainSimulation.tick` enters `contact.reason() != "ready"`, commits the last clear pose, then unconditionally assigns `t.speed = 0` at the current collision handling point (historically ~line 165), **before** calling `TrainDamage.impact`, regardless of whether the contact is a tiny 10-HP mob or a massive wall.
- `TrainDamage.impact` uses `TrainImpact.damage`; all entity contacts allocate the nominal energy budget half to target and half to stock. It currently returns `void`, gives no result to motion resolution and calls `Combat.damage` which itself returns `void`. No verification whether the entity actually died, was immune/protected, or remained blocking; damage callbacks may mutate train ownership. This is not the desired Factorio-style train-vs-mob flow.
- Existing `TrainCompletionGameTests.mobImpactUsesNativeDamageAttributionAndPreservesTrainCargo` **asserts the wrong invariant `t.speed == 0` for a cow at 1.1 source speed**. Revise it to the correct, justified behavior; do not merely delete the test.

**Source references / caveat:**
- https://wiki.factorio.com/Locomotive and https://wiki.factorio.com/Railway
- https://forums.factorio.com/viewtopic.php?t=121201 (2.0/2.1 era developer comparison: number of biters killed before momentum is lost)
- https://forums.factorio.com/viewtopic.php?t=68445 (empirical collision observations, not an authoritative exact engine formula).
The exact internal Factorio train collision solver is not open source; preserve its observed semantics and the public prototypes `weight`/`energy_per_hit_point` while **documenting** any bounded Minecraft adapter. Do not pretend an invented formula is source parity.

**Required implementation:**
1. Separate **pass-through lethal entity contact** from an actually **blocking entity contact** and from solid block/other-train/rail occupancy. A fast locomotive that kills an ordinary zombie, skeleton, cow, etc. must continue along its valid route without speed being reset to zero. Conversely an entity surviving the impact may genuinely impede a slow/weak train according to documented momentum/HP/resistance rules. Hits that are protected/cancelled or invulnerable must not be incorrectly treated as kills/pass-through; do not bypass PvP/team/pet claims or source impact resistance.
2. Introduce a deterministic **collision-resolution outcome** (e.g. target affected/killed, remaining kinetic budget, resulting speed, stop/continue), computed server-authoritatively using valid entity status, actual post-damage health/viability and source-scaled damage/resistance. Do **not** infer kill simply from the attempted damage amount; respect cancellable `hurt` results and game/mod invulnerability frames.
3. For a successful lethal impact, continue remaining distance for the current Minecraft tick when safe (or explicitly document a mathematically equivalent next-step continuation without false prolonged stall). Preserve source max speed and 3×60-Hz per MC tick integration, fuel payment exactly once per simulation tick, correct distance/route state and one authoritative train aggregate. If several mobs are hit in the same step, process in travel order with a **bounded** deterministic hit loop; never teleport through an uninspected wall or other train.
4. Use a **bounded per-step hit identity set** only to prevent replaying already resolved contacts, with a fresh collision test at later ticks as required. No arbitrary permanent immunity or damage every sample of the same overlap. When the mob survives, stop safely at last unblocked pose with justified speed change; no visual snap or position tunneling. Heavy entity/vehicle/stock handling must distinguish their actual collidable physical size and appropriate target vs train impact. Falling dead entities and item drops must not get counted as new solid wall blockers.
5. Reassess the half-to-stock damage rule for ordinary lethal mob hits against **observed Factorio train durability**, without silently making trains immortal. Train-on-train and wall impacts retain their distinct source-consistent damage model. Mob kill attribution must preserve direct rolling-stock projection / driver, correct damage type and multiplayer protections.
6. Be robust against death/removal callbacks that kill/retire/split the struck car or its train, or destroy the target and create drops. Ownership/fuel/health/cargo/fluid and occupancy reservations must be committed in a safe sequence before any callbacks; no double debit, invented velocity, orphaned passengers, duplicated wrecks or re-entrant tick crashes. Keep loaded-only graph checking and no forced chunk loading.
7. **Regression scenarios:** minimum one actual 259.2-km/h locomotive vs isolated regular mob (kills and proceeds); same speed through 3+ consecutive weak mobs; low-speed locomotive vs heavy/armored or protected surviving entity (may block); multi-car train with forward/rear impact; right-angle-side/bogie collision; wall and opposing stock still properly stop/conflict; dense crowd/stop-restart; curves and grades and train interaction; native server + real client movement and sound/effects. Test 120-km/h formerly crashing reverse/fractional route and separate-JVM saved fuel/position/UUID/cargo/fluid ownership. Include collision-at-a-rail-segment boundary and protected modded-living targets.
8. Benchmark bounded collision-heavy train movement (world reads, callbacks, time budget) versus the present baseline and keep all previously passing JUnit/native/CI tests. Change erroneous old assertions rather than weakening conservation/ownership/collision coverage. Document before/after actual `speed` and whether victim died, not merely absence of a crash.

**Acceptance:** in actual Minecraft gameplay at Factorio-maximum speed a train runs over a normal mob without an immediate full stop; the mob takes the intended impact damage and correct death/attribution, safe momentum/remaining-motion is retained, and genuine unkillable/structural/other-train obstacles still work.

## 7. Create-parity start tangent and bidirectional construction — user follow-up

**User-visible defect:** FactoryCraft still lays the new rail segment **away from the player**, even after selecting the starting track/point and turning around to face it or away from it. Although 0.31.1 implemented camera-following **destination tangent**, the **source-facing direction and actual source endpoint** are still rigid. The user requests a **near-faithful reproduction of Create's overall rail-building interaction**, with Factorio 2.1 track geometry/gameplay retained; direct code or assets copying is neither required nor authorized.

**Verified in current main (529feef at drafting):**
- `RailPlanner.target(level, hit, source, heading)` ranks existing endpoints primarily by **distance to hit**, using gaze-axis alignment only for **equal-distance ties**. For source selection, it returns the saved endpoint's one fixed orientation (`e == d.a() ? e.reverse() : e`), rather than considering both legal connection orientations/track ends and the eventual destination.
- `RailPlanner.click()` stores `Selection.start` once and `RailClient` caches it. Its current look-directed `destination()` adjusts only the **second point**. `RailCurve.plan(s.start(), end)` consequently remains biased toward the original selected fixed start tangent even if the player crosses the point and turns the camera around. `X` reverses `s.start()` manually, but the basic Create-like gesture must not require it.
- A ground click without a selected start creates `starter(end)` in exactly the gaze direction. This should be judged against Create's *actual* initial laying/connection behavior; avoid blindly assigning a heading simply because the player stands to one side.
- Current client 5×5 hints and preview share that fixed `start`, so adjusting only the final click would cause green ghosts disagreeing with placed rails.

**Read actual Create 1.21.1 implementation and compare end-to-end:**
- `TrackBlockItem.select`, `TrackBlockItem.useOn` — choosing track axis/source and beginning or clearing a connection:
  https://github.com/Creators-of-Create/Create/blob/mc1.21.1/dev/src/main/java/com/simibubi/create/content/trains/track/TrackBlockItem.java
- `TrackPlacement.tryConnect` — uses look angle to resolve target axis, can flip the **first axis** when `axis1.dot(end2 - end1) < 0` (lines ~182–189), and can flip the **second axis** when its intersection/parallel configuration would point the wrong way (lines ~192–204). Consider how these choices interact with snapped endpoints, curved rails, half-diagonals, and multi-axis junctions; also see its 5×5 valid-location hints and line preview:
  https://github.com/Creators-of-Create/Create/blob/mc1.21.1/dev/src/main/java/com/simibubi/create/content/trains/track/TrackPlacement.java
- `TrackBlockOutline.pickCurves` for actual curved-rail targeting and correct physical selection:
  https://github.com/Creators-of-Create/Create/blob/mc1.21.1/dev/src/main/java/com/simibubi/create/content/trains/track/TrackBlockOutline.java

**Implementation requirements:**
1. Separate **selected source physical rail/axis/endpoint identity** from **resolved source traversal tangent**. Choose which legal side and which endpoint to grow from using the selected track, the hovered destination, desired end tangent, and gaze. Do **not** treat the player's world position or the camera-to-source vector as the direction of the rail's forward growth.
2. For straight and single-axis existing rails, allow intuitive connection **in either geometric direction**: a source selected while standing on its north/south/east/west side should yield the **same rail** for the same desired world-space connection. Turning from facing the start to facing away from it, while standing in the same spot, must visibly and predictably affect the intended direction (where geometry permits). The heading of the **source track itself** never magically changes; resolve a valid outward tangent/which endpoint to attach.
3. When the hover destination changes across the source, **automatically resolve/flip** the source axis/endpoint if Create would, provided it does **not** move a saved existing endpoint or break a real connection. If the chosen anchor can't legally connect on the requested side, display a red preview with an explicit reason; do not build disconnected rails, generate a silent U-turn, or invent mid-edge topology. Existing `X` manual flip remains an optional override and should be reversible/resettable; do not require it for ordinary bidirectional extensions.
4. For a new start on ground (not yet a rail), ensure plain click places a real short paid segment oriented as the player **intentionally aims**, not always outward relative to the player's standing location. Compare Create's placement before and after selecting endpoints, and make the starter + continuation feel like one coherent workflow.
5. For a destination on another rail, snap to the physically correct axis/tangent and nearest *connectable* endpoint, not just the nearest visual projection; support legitimate source/destination reversal only with graph/tangent continuity. For turns, S-bends, slopes, diagonals/half-diagonals, shared nodes/junctions, preserve the source Factorio minimum radius and explicit graph identity. If several choices are real, show a predictable selection/highlight or provide an explicit alternate choice instead of silently picking by unstable tie.
6. **Single resolver for client and server**: move source/destination orientation decisions into a pure, deterministic shared planner function. Ghost geometry, Create-like 5×5 hints (green/red), cost, actual placed `RailPlan`, and final transaction must use that same result. Cache keys include source identity, selected side/manual override, hover destination position, gaze and relevant topology/world revision. Turning camera without moving the crosshair must update valid preview/indicators, including when looking back at the starting track.
7. Keep held-item switch/logout/C/sneak cancel, clear-after-success, ordinary reach, no chunk forcing, permissions/material ownership, atomic protected replacement, and 0.31.2 exact route intervals. No Create runtime dependency or protected assets; technical reference to open source is fine, but adhere to licenses if reusing code.
8. **Behavior matrix and real in-game tests**: build the same scenarios in a Create 1.21.1 test world and FactoryCraft if possible. Verify initial ground rail placement in opposite yaw directions, select an existing rail then face **toward vs away from it** from the same position, swap player side without changing endpoints, place to both sides of a long straight, connect two existing rails, reverse curved source, half-diagonal branch, 90° turn/S-bend, grade and junction, and rotate yaw while keeping the hovered block fixed. Assert preview geometry+hint status exactly match the committed server source/end IDs, cost/ownership and orientation; no unintended new rail segments or phantom refunds.
9. Keep testing appropriately scoped: targeted JUnit planning tests, native real-world placement/protection and a real client EN/RU screenshot sequence showing **both source directions**; check unchanged train movement and saving for actual modified rail graphs. Record what was observed rather than describing Create parity by implementation alone.

**Acceptance:** selecting a rail/point and then turning to face **toward or away from it**, or moving to the opposite side, does **not** force all new rails to grow in a player-relative “away” direction. Both lawful world-space directions and true Create-like source/destination snapping are accessible with intuitive camera/hover behavior. Client green preview, 5×5 hints and server-built geometry agree; no Factorio track or train invariants regress.
